# 교실용 수학 배틀 웹앱 기획서 (`plan.md`)

> **문서 목적**: 바이브코딩 도구(예: Claude Code, Cursor, Antigravity 등)에 그대로 제공해 MVP를 구현할 수 있도록 제품 방향, 화면, 기능, 데이터, 개발 순서, 완료 조건을 정의한다.
>
> **프로젝트 가칭**: 매쓰 아레나(Math Arena)  
> **문서 버전**: 0.2  
> **기획 기준**: 참고 사이트의 사용 흐름과 기능을 분석하되, UI·브랜드·문항·그래픽은 독자적으로 설계한다.
> **초기 출시 대상 학년**: 미확정(학년 결정 전 단계의 기획안). 학년별 문항 범위를 확정하지 않고, 추후 선택한 학년에 맞춰 교육과정과 문제 생성 규칙을 구체화한다.

---

## 1. 한 줄 소개

초등학생이 수학 문제를 풀며 경쟁하고 협력하는 **교사용 수학 게임 플랫폼**이다. 제품은 두 가지 플레이 방식을 제공하되, 개발 순서는 **① 교실 전자칠판/공용 화면에서 여러 학생이 함께 플레이 → ② 학생 개인 스마트폰·태블릿에서 접속하는 실시간 대결**로 고정한다. 두 방식은 같은 문제 엔진과 게임 규칙을 공유한다.

## 2. 기획 배경과 참고 아이디어

참고 사이트인 [킹수학 배틀](https://www.xn--9p4bn1ysod.com/kingmathbattle/?pub=ice)에서 다음과 같은 제품 패턴을 확인했다.

- 학년 및 단원, 문제 유형을 먼저 선택한 후 게임을 시작한다.
- 문제를 직접 고르거나 예시 문제를 확인할 수 있다.
- 키패드, 줄다리기, 축구, 슈팅, 캐치, 채점 등 서로 다른 플레이 방식이 제공된다.
- 1인 타임어택/랭킹전과 2~6인 대결 및 팀전이 함께 존재한다.
- 학생 이름이나 번호를 등록해 순서를 정하거나 무작위로 섞을 수 있다.
- QR 공유, 학급 기록, 개인 랭킹 등 수업 운영을 돕는 기능이 있다.

이 프로젝트는 위 아이디어를 참고하되, **교사가 1분 안에 게임을 설정하고 바로 수업에 활용할 수 있는 단순한 흐름**에 집중한다. 특히 사용자가 선택한 C 방식에 따라 공용 화면 플레이를 먼저 완성하고, 학생별 기기 접속은 2차 개발로 분리한다. 두 플레이 방식의 UI는 달라도 점수 계산, 정답 판정, 문제 진행 규칙은 공통 도메인 로직을 사용한다. 참고 사이트의 상표, 캐릭터, 이미지, 문항, 소스코드, 문구 및 고유한 화면 구성을 그대로 복제하지 않는다.

## 3. 목표와 성공 기준

### 3.1 제품 목표

1. 교사가 별도 가입이나 복잡한 설정 없이 즉시 게임을 시작할 수 있다.
2. 전자칠판·노트북·태블릿·스마트폰에서 레이아웃이 자연스럽게 동작한다.
3. 학습 내용과 게임 규칙을 분리해 새로운 단원과 게임 모드를 쉽게 추가할 수 있다.
4. 학생의 실제 이름 등 민감한 개인정보를 최소한으로 다루면서 수업 기록을 제공한다.
5. 1차는 서버 없이 한 기기에서 안정적으로 동작하게 하고, 2차 실시간 접속을 위해 게임 도메인과 통신 계층을 분리한다.
6. 바이브코딩으로 반복 개선하기 쉽도록 기능과 컴포넌트의 경계를 명확히 한다.

### 3.2 MVP 성공 기준

- 교사가 게임 설정부터 첫 문제 시작까지 60초 이내에 도달할 수 있다.
- 초등 수학 기본 연산 문제를 오류 없이 생성하고 채점한다.
- 2~6명이 **같은 전자칠판/공용 화면의 각자 입력 영역**을 사용해 키패드 배틀을 완료할 수 있다.
- 개인 타임어택을 실행하고 결과를 확인할 수 있다.
- 공용 화면 플레이는 네트워크 연결이나 학생 개인 기기 없이 완료된다.
- 2차 개발에 사용할 플레이 방식 구분(`shared-screen` / `personal-device`)과 세션 경계가 문서화되어 있다.
- 게임 종료 결과를 현재 기기에 저장하고 다시 조회할 수 있다.
- 데스크톱/전자칠판과 모바일 화면에서 핵심 기능을 사용할 수 있다.
- 새로고침이나 화면 크기 변경으로 진행 중 점수 및 정답 판정이 비정상적으로 바뀌지 않는다.

## 4. 주요 사용자와 사용 상황

| 사용자 | 필요 | 대표 상황 |
|---|---|---|
| 교사 | 빠른 설정, 학급 전체 참여, 쉬운 조작 | 수업 도입·정리, 연산 복습, 형성평가 |
| 학생 | 규칙 이해가 쉽고 즉각적인 피드백 | 전자칠판에서 친구와 대결하거나 개인 기기로 도전 |
| 관리자/제작자 | 문항·단원·게임 모드 확장 | 새 학년/단원 추가, 문제 오류 수정 |

### 기본 사용 시나리오

1. 교사가 홈 화면에서 `게임 시작`을 누른다.
2. 플레이 방식은 1차 기본값인 `교실 공용 화면`을 사용한다. (개인 기기 모드는 2차에서 활성화)
3. 학년, 학기, 단원, 문제 유형을 선택한다.
4. 게임 모드, 인원/팀, 제한 시간 또는 목표 점수를 설정한다.
5. 학생 별칭 또는 번호를 입력하고 순서를 정한다.
6. 미리보기에서 문항 난이도를 확인하고 `배틀 시작`을 누른다.
7. 게임 중 점수·남은 시간·현재 문제를 확인한다.
8. 종료 화면에서 승리자, 점수, 정답 수, 오답 수를 확인한다.
9. 결과를 현재 기기의 학급 기록에 저장하거나 다시 도전한다.

## 5. 제품 범위

### 5.1 MVP에 포함할 기능

- 반응형 웹앱 및 전자칠판 전체 화면 모드
- 학년/단원/문제 유형 선택 UI
- 기본 연산 문제 자동 생성
- 문제 미리보기 및 문제 수/난이도 설정
- 공용 화면 키패드 배틀(2~6인, 개인전 중심)
- 공용 화면에서 사용하는 플레이어별 큰 터치 입력 영역
- 줄다리기 배틀(1:1)
- 개인 타임어택(기본 60초, 시간 변경 가능)
- 학생 별칭/번호 입력, 순서대로/무작위 순서
- 플레이어별 색상/좌석 구분 및 접근성 있는 입력 피드백
- 점수, 정답/오답, 남은 시간, 승패 결과 화면
- 이 기기에 저장하는 최근 학급 기록
- 효과음 켜기/끄기, 다시 시작, 홈으로 이동
- 모바일·태블릿·데스크톱 대응(1차는 설정·개인 타임어택 및 관리 화면을 포함하며, 공용 화면 배틀은 가로형 대화면 우선)
- 플레이 방식 구조를 확장 가능하게 분리하되, 1차에서 원격 접속 기능은 노출하지 않음

### 5.2 다음 단계로 미룰 기능

- 축구·슈팅·캐치·채점 배틀 등 추가 게임 모드
- 2:2, 3:3, 2:2:2 팀전 및 토너먼트 대진표
- 학생 각자의 기기에서 접속하는 실시간 멀티플레이(2차 핵심 범위)
- 클라우드 기반 학급/학생 계정과 교사용 대시보드(개인 기기 대결 검증 후 필요성에 따라 도입)
- 온라인 전체 랭킹 및 학교별 랭킹
- 교사 직접 문항 제작/CSV 업로드/문항 묶음 공유
- 여러 과목 및 다국어 지원
- 학생별 성취 분석 및 학습 리포트

### 5.3 MVP 비목표(하지 않을 것)

- 초기 버전에서 회원가입·로그인을 필수로 하지 않는다.
- 학생의 실명, 전화번호, 이메일, 상세 학교 정보를 요구하지 않는다.
- 1차 MVP에서는 실시간 서버 대전이나 채팅을 구현하지 않는다. 학생 개인 기기 접속은 2차 단계에서만 추가한다.
- 문제 풀이와 무관한 광고, 결제, 소셜 기능을 넣지 않는다.
- 단원별 교육과정의 완전한 정합성을 한 번에 보장하려 하지 않는다. 먼저 범위를 제한해 검증한다.

## 6. 게임 모드 상세

### 6.1 키패드 배틀 — MVP 핵심

**목적**: 전자칠판 또는 교실 공용 디스플레이 한 대에서 2~6명이 각자 자기 입력 영역을 터치해 동시에 문제를 풀고 점수를 겨룬다. 이 방식은 1차 MVP의 최우선 기능이며 학생 개인 기기나 인터넷 연결을 요구하지 않는다.

- 화면을 플레이어 수만큼 영역으로 나눈다. 플레이어 수에 따라 2인 가로 분할, 3~4인 격자, 5~6인 2행/3열 등 읽기 쉬운 자동 배치를 적용한다.
- 각 플레이어 영역은 입력 영역 전체가 하나의 터치 타깃이 되도록 크게 설계한다. 학생이 전자칠판에 직접 접근하기 어려운 환경에서는 교사가 마우스/터치패드로 각 영역을 대신 조작할 수 있다.
- 1차 MVP의 기본 입력은 화면 터치/마우스이며, 물리 키보드의 플레이어별 멀티키 동시 입력은 필수 요구사항으로 두지 않는다.
- 각 플레이어 영역에 별칭, 점수, 연속 정답, 입력 키패드를 표시한다.
- 모든 플레이어는 같은 문제를 받는다. 답안 입력 방식은 공정성을 위해 플레이어마다 동일하게 유지한다.
- 키패드 배틀 기본 입력은 화면 숫자 키패드(0~9, 지우기, 제출)다. 각 플레이어 영역에 독립된 입력값을 유지해 다른 플레이어의 입력과 섞이지 않게 한다.
- 분수/소수 등은 MVP 범위에서 제외하고 정수 답을 기본으로 한다. 객관식 문항은 줄다리기 등 선택형 게임 모드에서 사용한다.
- 한 플레이어가 제출하면 해당 플레이어 영역만 잠기고 정오를 표시하며, 다른 플레이어는 계속 답할 수 있다.
- 모든 플레이어가 답했거나 문제 시간이 끝나면 정답과 해설을 짧게 보여준 뒤 다음 문제로 이동한다.
- 정답 점수는 기본 10점으로 하고, 오답은 0점으로 처리한다. 연속 정답 보너스는 옵션으로 제공할 수 있다.
- 마지막 문제 후 점수순으로 결과를 표시한다. 동점은 공동 순위로 처리한다.
- 진행 중 일시정지/재개/게임 종료는 교사 전용 컨트롤로 제공한다. 학생 입력 영역에는 교사 제어 버튼을 배치하지 않는다.
- 공용 화면 모드에서는 화면 분할과 글자 크기를 우선 최적화하며, 세로 화면에서는 안내 후 가로 화면 전환을 권장한다.

**초기 규칙 기본값**: 2~4인, 10문제, 문제당 15초. 5~6인 화면 배치는 별도 반응형 레이아웃을 적용한다. 교사가 학생 이름을 매번 입력하지 않도록 번호/별칭 템플릿과 직전 참가자 목록 재사용을 제공할 수 있으나, 최근 참가자 정보는 현재 기기에만 저장한다.

### 6.2 줄다리기 배틀 — MVP

**목적**: 1:1로 정답을 맞힐 때마다 중앙의 줄이 자기 쪽으로 이동한다.

- 좌우에 두 플레이어를 배치한다.
- 각 문제에 3개의 선택지를 표시한다.
- 정답을 선택하면 줄을 자기 쪽으로 1칸 이동한다.
- 오답이면 이동하지 않는다. 연속 정답 보너스는 추후 옵션으로 추가한다.
- 제한 시간 종료 또는 목표 이동 횟수 달성 시 승자를 결정한다.
- 학생 명단이 3명 이상이면 1:1 대진을 반복하는 토너먼트 모드는 후속 단계로 둔다.

### 6.3 개인 타임어택 — MVP

**목적**: 한 명이 정해진 시간 안에 최대한 많은 문제를 푼다.

- 기본 제한 시간 60초(교사가 30/60/90/120초 중 선택 가능).
- 정답 수, 오답 수, 정답률, 총점, 최고 연속 정답을 기록한다.
- 닉네임은 선택 입력이며 입력하지 않으면 임시 별칭을 사용한다.
- 개인 타임어택은 현재 기기에서 독립 실행한다.
- QR/방 코드로 다른 학생이 접속하는 기능은 2차 실시간 멀티플레이 범위다. 1차에서는 QR을 실제 참가 기능처럼 노출하지 않는다.

### 6.4 개인 기기 실시간 대결 — 2차 개발(선택 C의 후속 단계)

**목적**: 학생 각자가 스마트폰/태블릿으로 접속해 답안을 제출하고, 교사 화면에서 전체 진행과 점수를 확인한다. 이 기능은 1차 공용 화면 MVP가 출시되고 수업 현장에서 검증된 뒤 구현한다.

**교사 흐름**

1. 교사가 `개인 기기 모드`를 선택하고 게임 설정을 마친다.
2. 서버가 고유한 방 코드와 참가 URL을 발급한다. 교사 화면에 QR과 숫자/문자 코드를 함께 표시한다.
3. 학생은 QR 스캔 또는 짧은 URL로 접속해 방 코드와 별칭을 입력한다.
4. 교사 대기실에서 참가자 입장/퇴장 상태를 확인하고 참가자를 시작 전까지 제외할 수 있다.
5. 교사가 시작하면 문제·타이머·점수는 서버가 기준 상태로 관리하고 모든 화면에 동기화한다.
6. 게임 종료 후 교사 화면에 결과가 표시되고, 저장 동의/정책에 따라 기록을 보관한다.

**학생 흐름**

- 최초 입장 시 별칭만 입력하며 회원가입은 요구하지 않는다.
- 대기실에서는 입장 완료 상태와 시작 대기 안내만 표시한다.
- 게임 중 학생 기기에는 문제와 큰 답안 선택지/숫자 입력 UI를 제공한다. 교사 화면에는 학생별 정답 입력값을 노출하지 않고 전체 진행과 점수만 표시할 수 있다.
- 한 문제당 한 번만 제출할 수 있으며 제출 후 수정은 허용하지 않는 것을 기본 규칙으로 한다.
- 연결이 끊겨도 방이 유효하고 제한 시간이 남아 있으면 같은 참가자 토큰으로 재접속할 수 있도록 설계한다.

**2차 기술·운영 규칙**

- 방 생성/참가/정답 제출/점수 반영의 최종 권한은 서버에 둔다. 브라우저 클라이언트가 전송한 점수를 그대로 신뢰하지 않는다.
- 문제별 서버 기준 시작 시각과 마감 시각을 사용해 기기 시계 차이로 인한 불공정을 줄인다.
- 참가자별 중복 제출과 세션이 끝난 후 늦은 제출은 서버에서 거부한다.
- 방 코드는 추측하기 어렵게 생성하고, 방 종료 또는 일정 시간 비활성 후 만료시킨다. 기본 만료 정책은 구현 시 확정한다.
- 연결 상태는 `waiting`, `connected`, `reconnecting`, `disconnected`, `removed` 등으로 구분한다.
- 학생에게는 별칭 외의 개인정보를 요구하지 않는다. 접속 IP 등 서비스 운영 로그의 수집 여부와 보관 기간은 배포 전 별도 검토한다.

**2차 완료 조건**: 교사 방 생성 → 학생 2명 이상 입장 → 교사 시작 → 학생 기기 답안 제출 → 모든 클라이언트의 점수 동기화 → 연결 재시도 → 결과 확인이 실제 네트워크 환경에서 가능해야 한다.

### 6.5 확장 게임 모드 후보

| 모드 | 기본 플레이 | 우선순위 |
|---|---|---|
| 축구 배틀 | 정답이 적힌 골대를 선택해 슛, 골키퍼 난이도 설정 | P2 |
| 슈팅 배틀 | 정답 영역을 맞혀 상대 영역을 밀어내기 | P2 |
| 캐치 배틀 | 움직이는 선택지 중 정답을 잡기 | P2 |
| 채점 배틀 | 제시된 풀이/답이 맞는지 빠르게 판정 | P3 |

각 게임 모드는 공통 문제 엔진과 점수/세션 API를 재사용해야 한다.

## 7. 문제 엔진

### 7.1 MVP 문항 범위

초기에는 `덧셈`, `뺄셈`, `곱셈`, `나눗셈` 중 선택한 유형을 지원한다. 문제 생성기는 학년별 범위 설정을 사용하고, 초기에 확정하지 못한 교육과정 세부 단원은 설정 파일로 관리한다.

- 덧셈/뺄셈: 자릿수와 받아올림/내림 여부를 난이도 설정으로 제어한다.
- 곱셈: 곱하는 수의 범위와 구구단 범위를 제어한다.
- 나눗셈: 기본값은 나누어떨어지는 문제로 제한하고, 나머지 있는 나눗셈은 옵션으로 제공한다.
- 음수 허용 여부, 분수/소수 등은 학년·단원 설정에서 명시적으로 켠 경우에만 출제한다.

### 7.2 문항 데이터 형식

```ts
export type Operation = 'addition' | 'subtraction' | 'multiplication' | 'division';
export type Difficulty = 'easy' | 'normal' | 'hard';

export interface MathQuestion {
  id: string;
  prompt: string;             // 예: "28 + 17 = ?"
  answer: number;
  choices?: number[];         // 객관식 모드에서 사용
  operation: Operation;
  difficulty: Difficulty;
  grade?: number;
  unitId?: string;
  explanation?: string;
}
```

### 7.3 문제 생성 품질 규칙

- 정답은 반드시 수식 계산 결과와 일치해야 한다.
- 선택지는 정답과 중복되지 않아야 하며, 선택지끼리도 중복되지 않아야 한다.
- 선택지는 음수/분수 등 학년 범위를 벗어나지 않아야 한다.
- 같은 세션 안에서 동일 문항이 지나치게 반복되지 않도록 한다.
- 0으로 나누기, 나누어떨어지지 않는 나눗셈 등 허용하지 않은 케이스를 차단한다.
- 문항 생성 함수를 UI 컴포넌트 안에 직접 작성하지 않고 별도 모듈로 분리한다.
- 난수 생성기를 주입할 수 있게 만들어 테스트에서 동일한 결과를 재현할 수 있도록 한다.

### 7.4 문항 직접 제작(후속)

교사가 직접 문항을 입력하고 저장할 수 있도록 다음 필드를 고려한다: 문제 문구, 정답, 선택지, 해설, 학년, 단원, 태그, 난이도. MVP는 자동 생성에 집중하고 사용자 제작 문항은 P2로 둔다.

## 8. 화면 및 내비게이션

### 8.1 화면 목록

| 화면 | 주요 구성 | 핵심 동작 |
|---|---|---|
| 홈/설정 | 로고, 학년·단원·유형, 플레이 방식, 게임 모드 카드, 시작 버튼 | 1차는 공용 화면 모드로 진입 |
| 문제 미리보기 | 샘플 문제, 난이도, 출제 수, 시간 | 문제 확인 및 설정 수정 |
| 학생 설정 | 플레이어 수, 별칭/번호 입력, 순서 설정 | 공용 화면에서 플레이어 등록 |
| 개인 기기 대기실(2차) | 방 코드, QR, 참가자/연결 상태 | 원격 참가자 확인 및 게임 시작 |
| 학생 답안 화면(2차) | 문제, 답안 입력, 제출 상태 | 개인 기기에서 답 제출 |
| 게임 화면 | 문제, 타이머, 점수판, 플레이어 입력 영역 | 답 제출 및 진행 |
| 결과 화면 | 순위, 점수, 정답률, 재도전 | 기록 저장, 다시 하기 |
| 학급 기록 | 최근 게임 목록, 날짜, 참가자, 점수 | 기록 조회/삭제 |
| 도움말/설정 | 게임 규칙, 효과음, 화면 설정 | 옵션 변경 |

### 8.2 홈 화면 기본 배치

1. 상단: 서비스명, 도움말, 설정.
2. 플레이 방식: 1차는 `교실 공용 화면`을 기본값으로 선택한다. `학생 개인 기기`는 2차 배포 전까지 숨기거나 `2차 업데이트 예정`으로 비활성 표시한다.
3. 학습 범위: 학년 → 학기 → 단원 → 문제 유형 선택.
4. 게임 모드: 카드형으로 키패드 배틀/줄다리기/개인 타임어택과 인원 정보를 표시한다.
5. 참여자: 공용 화면 대결이면 인원 선택 및 별칭/번호 입력. 개인 타임어택이면 1명만 입력한다.
6. 게임 옵션: 문제 수, 제한 시간, 난이도.
7. 하단 고정 CTA: `게임 시작`.

선택 단계는 점진적으로 노출해 첫 화면이 복잡해지지 않게 한다. 필수 설정을 선택하지 않았을 때는 실행 버튼을 비활성화하고 필요한 항목을 바로 안내한다.

### 8.3 디자인 원칙

- 밝고 경쾌한 교실 분위기. 단, 화면 전체를 과도한 장식으로 채우지 않는다.
- 전자칠판에서는 멀리서도 읽을 수 있도록 큰 글자와 높은 대비를 사용한다.
- 모바일에서는 터치 영역을 넉넉하게 하고 한 손 조작을 고려한다.
- 정답/오답을 색상만으로 구분하지 않고 아이콘과 텍스트를 함께 제공한다.
- 게임 중에는 점수, 현재 문제, 타이머 외의 불필요한 정보를 숨긴다.
- 효과음/애니메이션은 끌 수 있어야 하며, 모션 감소 설정을 존중한다.
- 태블릿 가로/세로, 데스크톱, 전자칠판 해상도에서 레이아웃을 검증한다.

## 9. 데이터와 상태 관리

### 9.1 핵심 타입

```ts
export type PlayChannel = 'shared-screen' | 'personal-device';
export type GameMode = 'keypad' | 'tug-of-war' | 'solo';
export type SessionStatus = 'setup' | 'waiting' | 'countdown' | 'playing' | 'paused' | 'finished' | 'cancelled';

export interface GameSettings {
  /** 접속/진행 방식: 1차는 shared-screen만 구현 */
  playChannel: PlayChannel;
  /** 실제 게임 규칙/미니게임 */
  gameMode: GameMode;
  grade: number;
  semester?: 1 | 2;
  unitId?: string;
  operations: Operation[];
  difficulty: Difficulty;
  questionCount: number;
  timeLimitSeconds: number;
  playerCount: number;
  pointsPerCorrectAnswer: number;
}

export interface Player {
  id: string;
  displayName: string;
  seatIndex: number;
  colorKey: string;
  score: number;
  correctCount: number;
  incorrectCount: number;
  /** 2차 개인 기기 모드에서만 사용 */
  connectionStatus?: 'local' | 'connected' | 'reconnecting' | 'disconnected' | 'removed';
}

export interface GameSession {
  id: string;
  status: SessionStatus;
  settings: GameSettings;
  players: Player[];
  currentQuestionIndex: number;
  startedAt?: string;
  finishedAt?: string;
  /** 2차 개인 기기 모드에서 서버가 발급 */
  roomCode?: string;
}

export interface BattleRecord {
  id: string;
  createdAt: string;
  playChannel: PlayChannel;
  gameMode: GameMode;
  settings: GameSettings;
  players: Player[];
  winnerPlayerIds: string[];
  durationSeconds: number;
}
```

### 9.2 저장 정책

- MVP는 브라우저 `localStorage`에 최근 100개 기록을 저장한다.
- 기록 삭제 기능을 제공하고, 저장 데이터가 현재 브라우저/기기에 한정됨을 사용자에게 명확히 알린다.
- 학생 실명 대신 별칭 또는 번호 사용을 기본 안내한다.
- 2차 개인 기기 모드에서도 학생 회원가입을 필수로 하지 않고 별칭 중심으로 운영한다.
- 클라우드 저장이 필요해지면 교사 계정과 학급 코드 기반으로 확장하되, 저장 항목과 보관 기간을 다시 설계한다.

### 9.3 상태 관리 원칙

- 게임 세션 상태(현재 문제, 타이머, 플레이어 응답, 점수)를 UI와 분리된 도메인 계층에서 관리한다.
- 플레이 방식(`shared-screen` / `personal-device`)과 게임 모드(`keypad` / `tug-of-war` / `solo`)는 서로 다른 개념으로 모델링한다. 개인 기기 접속은 게임 모드가 아니라 플레이 방식이다.
- 1차에서는 `LocalSessionController`가 같은 기기 안에서 모든 참가자 상태를 관리한다. 2차에서는 동일한 게임 도메인 명령/이벤트를 네트워크로 전달하는 컨트롤러를 추가한다.
- UI 컴포넌트가 localStorage나 네트워크 API를 직접 호출하지 않도록 저장소/통신 어댑터를 분리한다.
- 타이머는 화면 렌더링과 분리하고, 중복 interval이 생성되지 않게 정리한다.
- 문제 전환과 점수 반영은 단일 함수/리듀서에서 처리한다.
- 한 플레이어가 한 문제에 두 번 제출할 수 없도록 응답 상태를 잠근다.
- 화면 새로고침 시 진행 중인 게임을 복구하지 않는 MVP 정책을 기본으로 하되, 종료된 기록은 저장한다.

### 9.4 플레이 방식별 책임 분리(중요)

| 구분 | 1차: 공용 화면(`shared-screen`) | 2차: 개인 기기(`personal-device`) |
|---|---|---|
| 실행 기기 | 교사 노트북/전자칠판 한 대 | 교사 화면 + 학생별 스마트폰/태블릿 |
| 학생 참여 | 한 화면의 개인별 터치 영역 | 학생 기기에서 방 코드/QR로 입장 |
| 네트워크 | 게임 진행에 불필요 | 실시간 통신 필수 |
| 점수 권한 | 브라우저의 단일 세션 엔진 | 서버가 최종 점수/진행 상태 관리 |
| 참가자 식별 | 좌석 번호/별칭 | 방 안에서 중복되지 않는 별칭 또는 참가 ID |
| 기록 | localStorage | 세션 결과 저장 정책 별도 설계 |

**핵심 설계 원칙**: 게임 규칙과 문제 생성은 플레이 방식과 무관한 순수 로직으로 둔다. `shared-screen`은 같은 브라우저에서 그 로직을 호출하고, `personal-device`는 서버를 통해 동일한 명령을 전달한다. 두 방식을 위해 점수 계산이나 정답 판정 코드를 복제하지 않는다.

`SessionController` 인터페이스는 1차에서 필요한 최소 기능만 정의한다. 최소 명령은 `startSession`, `submitAnswer`, `pauseSession`, `resumeSession`, `finishSession`이며, 게임 엔진은 이 명령의 유효성/점수 반영을 담당한다. 2차용 실시간 구현체는 실제 백엔드 선정 후 추가하며, 1차 릴리스에 미완성 네트워크 버튼·가짜 방 코드·작동하지 않는 QR을 노출하지 않는다.

## 10. 권장 기술 구성

MVP는 서버 없이도 동작하는 단순한 구조로 시작한다.

- **앱**: React + TypeScript + Vite
- **스타일**: Tailwind CSS 또는 프로젝트에 이미 적용된 일관된 CSS 시스템 중 하나만 선택
- **라우팅**: React Router(화면 수가 늘어날 경우)
- **상태**: React Context/Reducer로 시작. 복잡도가 실제로 커질 때 Zustand 도입
- **저장**: localStorage
- **테스트**: Vitest + React Testing Library
- **배포**: 정적 웹 호스팅(Vercel, Netlify 등)
- **2차 실시간 멀티플레이**: Supabase Realtime 또는 별도 WebSocket 서버를 비교해 선택한다. 선택 전까지 서버 기능을 선제 구현하지 않는다.

초기부터 로그인, 데이터베이스, 실시간 서버를 모두 도입하지 않는다. 다만 게임 엔진과 저장소를 인터페이스로 분리해 향후 서버 저장으로 교체할 수 있게 한다.

## 11. 개발 순서 및 작업 단위

### Step 1 — 앱 뼈대와 홈 화면

- 프로젝트 실행 및 기본 레이아웃 구축
- 반응형 디자인 토대 구성
- 플레이 방식 상태는 `shared-screen`을 기본값으로 고정(개인 기기 옵션은 미노출)
- 학년/단원/유형/게임 모드 선택 상태 구현
- 샘플 데이터로 홈 화면 완료

**완료 조건**: 모바일 및 데스크톱에서 설정 UI가 깨지지 않고 선택값이 유지된다.

### Step 2 — 문제 생성 엔진

- 연산별 문제 생성기 구현
- 난이도 및 범위 규칙 적용
- 객관식 선택지 생성
- 단위 테스트 작성

**완료 조건**: 최소 500개의 무작위 생성 케이스를 검증해 정답·선택지 규칙 위반이 없다.

### Step 3 — 키패드 배틀

- 플레이어 등록 및 순서 설정
- 2~6인 화면 분할
- 답 입력, 정오 피드백, 점수 계산
- 문제 전환, 타이머, 일시 정지/종료

**완료 조건**: 2인 및 4인 플레이를 처음부터 결과 화면까지 완료할 수 있고, 중복 제출/시간 초과 처리가 정상 동작한다.

### Step 4 — 줄다리기와 개인 타임어택

- 줄다리기 상태 및 승리 판정
- 개인 타임어택과 통계 계산
- 결과 화면 공통화

**완료 조건**: 두 모드 모두 공통 문제 엔진을 사용하며 결과 기록 형식이 동일하다.

### Step 5 — 기록 및 수업 편의 기능

- localStorage 저장/불러오기
- 최근 100회 목록, 상세 결과, 전체 삭제
- 현재 기기에서 공유 가능한 설정 프리셋이 있다면 링크 복사만 제공하고, 참가용 QR/방 코드는 2차에서 구현
- 효과음/전체 화면 옵션

**완료 조건**: 새로고침 후 종료 기록이 남아 있고, 기록 삭제가 실제 저장소에도 반영된다.

### Step 6 — 1차 품질 검증 및 배포

- 크롬/엣지 기반 전자칠판 및 모바일 브라우저 테스트
- 입력 오류, 화면 크기, 오디오 권한, 타이머 정리 검증
- 접근성 및 개인정보 최소 수집 확인
- 배포 및 간단한 사용 가이드 작성

**완료 조건**: 공용 화면 배틀/줄다리기/개인 타임어택의 핵심 수용 기준을 모두 통과하고 공개 URL에서 새 세션을 시작할 수 있다. 학생 개인 기기 접속은 이 단계의 완료 조건이 아니다.

### Step 7 — 개인 기기 실시간 플레이(2차)

- 실시간 백엔드와 방 생성/만료 기능 설계
- 교사 호스트 화면의 대기실 및 QR/코드 표시
- 학생 참가 화면과 별칭 입력/재접속 토큰 구현
- 서버 권한 기반 문제 진행, 제출 마감, 점수 계산 구현
- 연결 끊김/재접속/늦은 참가/중복 제출 처리
- 실제 교실 Wi-Fi 환경에서 동시 접속 부하와 기기별 동기화 테스트

**완료 조건**: 최소 30명 동시 참가를 목표로 시험하고, 연결이 불안정한 일부 참가자가 있어도 전체 세션의 점수와 진행 상태가 일관되게 유지된다. 이 목표치는 부하 테스트로 검증하며 보장 성능으로 간주하지 않는다.

## 12. 테스트 시나리오 및 수용 기준

### 기능 테스트

- 학년/단원/문제 유형을 선택하지 않았을 때 적절한 안내를 보여준다.
- 덧셈·뺄셈·곱셈·나눗셈 문제의 정답이 정확하다.
- 객관식 선택지에는 정답이 정확히 한 번 포함된다.
- 플레이어 2~6명 등록 시 각자 다른 입력 영역이 제공되고, 입력은 해당 영역에서만 가능하다.
- 2~6인 공용 화면 레이아웃에서 핵심 텍스트/선택지가 겹치지 않는다.
- 한 플레이어가 답을 제출해도 아직 제출하지 않은 플레이어의 입력은 활성 상태로 유지된다.
- 한 플레이어의 중복 답안이 점수에 두 번 반영되지 않는다.
- 제한 시간 0초가 되면 입력을 막고 결과 또는 다음 문제로 전환한다.
- 동점 결과가 임의로 한 명의 승리로 처리되지 않는다.
- 기록 저장 후 브라우저를 새로 열어도 기록이 남는다.
- 기록 전체 삭제 후 목록이 비어 있다.

### UX 테스트

- 수업 중 교사가 60초 안에 게임 시작 설정을 마칠 수 있다.
- 모바일에서 모든 버튼과 선택지가 손가락으로 누르기 쉽다.
- 전자칠판에서 문제와 점수판을 교실 뒤쪽에서도 읽을 수 있다.
- 효과음이 차단되어도 게임 진행이 멈추지 않는다.
- 오답/정답 정보가 색상 외의 표현으로도 전달된다.

### 12.1 플레이 방식 C의 단계별 출시 기준

**1차 MVP 출시 전 반드시 확인**

- 교사 기기 한 대만으로 게임 생성·시작·종료가 가능하다.
- 공용 화면 키패드 배틀에서 2~6명 각자 입력/제출/점수 반영이 가능하다.
- 학생 개인 휴대전화가 없어도 수업이 완결된다.
- 네트워크가 끊겨도 공용 화면 게임 자체는 영향을 받지 않는다(기록 저장 등 브라우저 기능은 예외).
- 게임 종료 기록이 동일 브라우저에서 다시 확인된다.

**2차 개인 기기 모드 착수 조건**

- 1차 MVP의 교실 실사용 피드백을 반영한다.
- 동시 접속 목표 인원, 학교 네트워크 제약, 서버 예산/운영 주체를 결정한다.
- 실시간 백엔드 후보를 비교하고 연결 끊김·재접속 정책을 확정한다.
- 별칭/방 코드 방식의 개인정보 및 보안 검토를 마친다.

## 13. 바이브코딩 에이전트 실행 지침

아래 원칙을 모든 구현 단계에서 지킨다.

1. **한 번에 전체 서비스를 만들지 않는다.** 각 Step을 완료하고 실행/검증한 뒤 다음 단계로 이동한다.
2. 구현 전 현재 프로젝트 파일과 기술 스택을 먼저 확인한다. 이미 존재하는 설정을 불필요하게 교체하지 않는다.
3. 화면을 만들기 전에 타입과 핵심 상태 전이를 정의한다.
4. 문제 생성·점수 계산·승리 판정은 UI와 분리하고 테스트 가능한 순수 함수로 작성한다.
5. 임시 데이터와 실제 기능을 명확히 구분한다. 동작하지 않는 버튼이나 가짜 랭킹을 완성된 기능처럼 노출하지 않는다.
6. 기능을 추가할 때 기존 게임 모드가 깨지지 않도록 회귀 테스트를 실행한다.
7. 모바일/전자칠판에서 실제 터치와 큰 화면을 모두 검증한다.
8. 불필요한 의존성, 과도한 추상화, 조기 서버 도입을 피한다.
9. 접근성, 개인정보 최소 수집, 사용자의 기록 삭제 가능성을 기본값으로 고려한다.
10. 각 작업 종료 시 변경 파일, 실행 방법, 테스트 결과, 남은 이슈를 요약한다.

plan.md를 먼저 읽고, 확정된 플레이 방식 C의 개발 순서를 이해했는지 요약해줘.
1차 MVP는 교실 공용 화면(shared-screen)이다. 학생 개인 기기(personal-device) 접속/QR 방 입장/실시간 서버 통신은 2차 범위이므로 지금 구현하지 마.
현재 프로젝트 구조와 설치된 의존성을 먼저 점검한 뒤, 문서의 Step 1만 구현해줘.
기존 프로젝트 설정은 불필요하게 바꾸지 말고, 아직 구현하지 않은 기능은 완료된 것처럼 표시하지 마.
구현 후 실행 방법과 테스트 방법을 안내하고, 발생한 오류를 직접 수정해줘.

## 14. 가정 및 추가 결정이 필요한 사항

현재 정보가 없어 다음과 같이 기본 가정했다. 실제 제작 전 아래 항목을 확정하면 기획을 더 정확하게 조정할 수 있다.

| 항목 | 기획서의 기본 가정 | 확인이 필요한 이유 |
|---|---|---|
| 첫 출시 대상 학년 | 미확정 | 학년별 수 범위·단원·성취기준이 달라지므로 사용자 결정 후 확정 |
| 과목 | 수학 우선 | 다른 과목은 문항 구조와 게임 규칙이 달라질 수 있음 |
| 플레이 방식 | 1차: 전자칠판/공용 화면에서 2~6명 대결 + 개인 타임어택. 2차: 학생 개인 기기 접속 대결 | 두 방식의 화면과 접속 흐름은 다르지만 문제 엔진/게임 규칙을 공유하도록 설계 |
| 저장 | 1차: 로그인 없이 현재 기기에 저장. 2차: 방/세션 실시간 상태는 서버에서 처리하고 영구 기록은 별도 정책 결정 | 기록 공유와 보관 범위에 따라 백엔드/개인정보 정책이 달라짐 |
| 콘텐츠 범위 | 사칙연산으로 MVP 시작 | 교육과정 단원 전체를 넣으려면 문항 데이터 설계가 필요함 |
| 브랜딩 | 가칭 매쓰 아레나 | 서비스명, 캐릭터, 컬러 시스템 확정 필요 |

### 제작 전 추가로 확정하면 좋은 정보

플레이 방식은 **C로 확정**되었으므로 다시 선택할 필요가 없다. 다만 첫 출시 대상 학년은 아직 정하지 않은 상태이며, 이 문서에는 특정 학년의 교육과정·단원·문항 범위를 반영하지 않는다. 남은 결정 사항은 다음과 같다.

- **초기 대상 학년**: 아직 결정하지 않는다. 이 문서는 첫 출시 학년을 정하기 전까지의 기획 상태를 보존하며, 특정 학년이나 학기·단원을 전제로 한 문항 범위는 확정하지 않는다. 학년이 결정되면 해당 학년의 교육과정과 성취기준을 확인해 MVP 범위를 다시 구체화한다.
- **초기 단원/연산**: 사칙연산 중심의 정수 연산은 문제 엔진을 설계하기 위한 임시 기본 가정이다. 첫 출시 학년과 단원이 정해지기 전에는 실제 출제 범위나 교육과정 정합성이 확정된 것으로 간주하지 않는다.
- **수업 기기 환경**: 전자칠판 터치 입력을 주로 쓸지, 교사 노트북과 프로젝터/마우스를 주로 쓸지에 따라 공용 화면 입력 영역의 크기와 조작 방식을 조정한다.
- **참여 인원**: 기본은 2~4인, 최대 6인이다. 실제 교실 운영 방식에 따라 한 번에 참여할 팀/학생 수를 조정한다.
- **브랜딩**: `매쓰 아레나`는 가칭이다. 서비스명, 캐릭터/일러스트 사용 여부, 색상 방향은 추후 확정한다.

개인 기기 모드(2차)에 착수할 때는 동시 접속 목표 인원, 학교 Wi-Fi 환경, 서버 예산/운영 주체, 세션 기록의 클라우드 저장 필요성을 별도로 확정한다. 위 항목이 아직 정해지지 않아도 1차 화면과 게임 엔진 개발은 기본 가정으로 시작할 수 있다.
